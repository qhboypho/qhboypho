## Required rollout gates — owner approval first

1. Confirm the full promotion scope and an agreed maintenance window. A write
   pause is required: old checkout writers must not run against new reservation
   triggers. Establish and test the maintenance mechanism before changing D1;
   do not improvise database changes on a busy site.
2. Provision separate staging D1/R2/chat resources before an online preview.
   Preview bindings intentionally inherit none of production's resources.
   Rehearse the candidate there with synthetic credentials/provider mocks.
3. Review the existing namespace inventory and deploy `wrangler.chat.jsonc`.
   The Worker is private (no workers.dev or preview URL), owns the chat class
   and daily expired-chat cleanup. Verify that retention policy is intended.
4. Pause mutations, drain in-flight writes, record the latest deployment, take
   a fresh private backup and rerun the rehearsal. Account for pending payment
   callbacks and ambiguous shipping attempts; never replay them blindly.
5. Apply exactly the four reviewed pending migrations to the verified D1,
   then deploy the matching Pages bundle with `--branch ui-new-v1`. The
   `npm run deploy:prod` command runs the local release gate first but does NOT
   perform the backup, maintenance pause or migrations for the operator.
6. Configure scheduler credentials securely and deploy `wrangler.payments.jsonc`
   only after the matching schema and application are healthy. Do not assume
   Pages secrets are inherited, and do not copy unverified local keys.
7. Verify webhook registration, owner-supervised low-value PayOS acceptance,
   COD order recording, unpaid-order shipping block, and carrier sandbox flow.
   Check scheduler logs and the reconciliation queue before reopening.
8. Monitor order creation errors, duplicate attempts, payment review items and
   carrier timeouts. Do not issue refunds, live shipments or test orders without
   their specific approval.

Do not restore only the old Pages bundle after installing the reservation
triggers. Keep mutations paused and forward-fix, or restore a coordinated
database/application snapshot only after reconciling all intervening external
payments and carrier records. Keep immutable payment audit records intact.
